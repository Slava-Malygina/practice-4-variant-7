# Отчёт по практической работе №4. Вариант 7

## Тема
Мокирование очередей сообщений Kafka / RabbitMQ.

## Что тестируется
Метод `EventPublisher.publish_order_created(order_id, amount)`.
Он должен отправить событие `OrderCreated` в Kafka-топик `orders`.

## Стратегия мокирования
Реальный `KafkaProducer` заменяется на `unittest.mock.Mock`.
Это позволяет:
- не запускать Kafka-брокер;
- проверить факт вызова `send()`;
- проверить аргументы вызова: topic и JSON-payload;
- смоделировать ошибку брокера через `side_effect`.

## Замокированные артефакты
- `KafkaProducer` — внешняя зависимость.
- Метод `KafkaProducer.send()` — граница взаимодействия с брокером.

## Проверяемые сценарии
1. Позитивный: `send()` вызван один раз с `topic="orders"`.
2. Позитивный: payload — корректный JSON с полями `type`, `orderId`, `amount`.
3. Негативный: если `send()` выбрасывает исключение, оно не подавляется.

## Плюсы мокирования
- Тесты быстрые и изолированные.
- Не требуется инфраструктура Kafka.
- Легко проверять параметры вызова и ошибки.

## Минусы
- Не проверяется реальная совместимость с Kafka.
- Можно случайно замокировать слишком много и получить хрупкий тест.
- Контракт брокера проверяется только косвенно.

## Альтернативы
- Testcontainers с реальным Kafka.
- Embedded Kafka / in-memory fake producer.
- Интеграционные тесты с docker-compose.

## Ответы на контрольные вопросы

### 1. В чём разница между mock и stub?
Stub возвращает заранее заданные данные и нужен для управления состоянием.
Mock дополнительно позволяет проверять взаимодействия: сколько раз вызван метод, с какими аргументами.

Пример stub:
```python
producer.send = lambda topic, value: None
```

Пример mock:
```python
producer = Mock()
publisher.publish_order_created("ord_1", 500.0)
producer.send.assert_called_once_with("orders", ANY)
```

### 2. Может ли избыточное мокирование привести к «зелёным, но бесполезным» тестам?
Да. Если замокировать внутренние методы класса, тест начинает проверять реализацию, а не поведение. При рефакторинге без изменения поведения тест может упасть, хотя код работает корректно.

### 3. Как проверить, что мок-объект был вызван именно с такими параметрами?
Через `assert_called_once_with(...)`, `assert_called_with(...)`, `call_args`, `call_args_list`.

Пример:
```python
producer.send.assert_called_once()
args, kwargs = producer.send.call_args
assert args[0] == "orders"
```

### 4. Как избежать «хрупкости тестов» при мокировании?
Мокировать только внешние зависимости: API, БД, очередь, файловую систему.
Не мокировать приватные методы и внутренние детали реализации.
Проверять наблюдаемое поведение и контракты, а не последовательность внутренних вызовов.
```
